# 经验教训

> 快照：2026-11-01，版本 `2.0.37+39`。本文复盘的是“系统与流程为何会让问题重复发生”，不是追责。
> 每条包含：现象 → 根因 → 已做修复 → 预防规则 → 应补测试。

## 摘要

最近五类问题反复出现：拖动落位、名单数量、更新缓存、表单布局、字体许可。共同点不是“某次改错了”，而是：

1. 缺少可重复的验收：没有测试，只靠截图和“看起来好了”；
2. 状态有多个写入者：同步、回前台、导入、拖动各自改 `schedule`；
3. 缓存/版本被当成常量：URL、build、名单数量都不会随内容变化；
4. 用一次性 `str.replace` 脚本改源码，替换失败也静默通过；
5. 许可与合规没有进入发布门禁。

## L1 拖动：手势竞技场与滚动抢夺

**现象**：`LongPressDraggable + DragTarget` 版本松手不落位；拖动时背景横向/纵向滚动；偶尔一次拖动生成两个浮层；同一问题从 2.0.29 修到 2.0.37 共 9 个版本。

**根因**

- 拖拽库自己有手势识别器，与外层 `ListView`/`SingleChildScrollView` 争竞技场；长按未赢得竞技场前，轻微移动就被判定为滚动。
- `DragTarget` 的命中区域在滚动后与指针位置不一致；`onAccept` 拿到的是 target 数据，不是可靠坐标。
- 在 `onLongPressStart` 里 `setState` 重建了手势组件，识别器被销毁，后续 `move/end` 丢失。
- 连续多个版本都在换实现（DropTarget → 整周 target → Overlay → 原始 Pointer），但没有一份固定的坐标契约和测试。

**已做修复**（2.0.34–2.0.37）：改为 `GestureDetector` 长按 + 根 `Overlay` 浮层 + `gridKey.globalToLocal` 网格坐标；拖动开始时把横向滚动 `physics` 置为 `NeverScrollableScrollPhysics`，结束恢复。

**预防规则**

- 一个交互只能有一个手势所有者；不要在拖动子树里再包 `Draggable`/`DragTarget`。
- 长按开始后**禁止重建**手势组件；用 `ValueNotifier`/`Overlay` 做局部更新。
- 用滚动容器的 `physics` 锁滚动，不要重建 `ScrollController` 或替换整个列表。
- 坐标换算必须是纯函数，网格 key 必须稳定（不能每次 `build` 新建 `GlobalKey`）。
- 落点语义写进注释：指针代表块的左上角还是中心，只允许一种。

**应补测试**

- 纯函数：`dx=0/87.9/88/615.9`、`dy=0/59.9/60/655.9` 的格号。
- Widget：`startGesture` → `pump(kLongPressTimeout + 50ms)` → move → up，断言 `moveMeeting` 参数。
- 拖动中触发一次 `notifyListeners()`，断言手势仍完成（防 `gridKey` 重建）。
- 取消路径：拖到时间栏/表头/网格外，断言无写盘。

## L2 浮层：重复插入与生命周期不对称

**现象**：快速长按/取消后偶发重复浮层（同一次拖动出现两个）；路由返回后浮层仍在。

**根因**

- 浮层在 `build`/`setState` 路径里插入，重建即重复插入。
- `_entry` 只在正常结束时移除；`dispose`、`onLongPressCancel`、路由 pop 没有统一清理。
- 用 `markNeedsBuild` 更新位置时，entry 可能已被移除，异常被吞。

**已做修复**：插入点移到 `onLongPressStart` 一次；`_end/_cancel/dispose` 统一 `remove` 并置空；浮层 `IgnorePointer`。

**预防规则**

- Overlay 生命周期必须“创建/销毁”成对，且写在一个 State 里；禁止跨组件持有。
- `remove()` 前判空、置空；`dispose` 兜底。
- 浮层内容只用 `ValueListenable` 更新，不依赖父级重建。

**应补测试**：连续 3 次开始-取消，断言 `Overlay` 中无残留；拖动中 pop 路由不抛异常。

## L3 远端名单：把“相对当前值”当成了下限

**现象**：一次远端返回 2 条旧 JSON，设置页从 350 所变成 2 所；后续加了 `if (list.length < schools.value.length) continue;` 才恢复。

**根因**

- 远端被当作权威源，直接覆盖内存列表。
- 守卫用“当前内存长度”做基准，而基准取决于 `assets/schools.json` 是否加载成功；加载失败时基准是 1，2 条旧数据即可通过。
- 只比较数量，不校验条目结构；`?v=350` 是常量，内容变化时 URL 不变，CDN 继续返回旧文件。

**已做修复**：内置 350 条作为首屏兜底；远端只覆盖内存、不落盘；数量守卫（部分有效）；黄山学院强制置顶。

**预防规则**

- 下限必须是**绝对常量**（`kMinSchoolCount = 350`），并与当前长度取 `max`。
- 远端数据是“增量建议”，不是权威；非法条目丢弃后重新计数。
- 缓存键必须随内容变化（版本/哈希），不能用固定 `v=350`。
- 任何“列表只增不减”都要有 fixtures：2、349、350、351、重名、坏 URL。

**应补测试**：删除本地资源后冷启动，远端 2 条仍被拒绝；351 条合法数据被接受；重名去重后计数正确。

## L4 数量回退：修复只挡住了“更少”，没挡住“更旧”

**现象**：2.0.25 修过一次“349 变 2”，2.0.27 恢复铜陵学院后总数 350；之后仍担心旧缓存把列表覆盖。

**根因**

- 修的是症状（数量），不是来源（缓存 + 信任模型）。
- 版本号、名单、构建号分散在 `pubspec.yaml`、`AppMeta`、`version.json`、文档四处，没有单一生成源。
- 发布脚本只改版本号，不改 `version.json` 的下载地址，导致 2.0.37 的元数据仍指向 v2.0.26。

**已做修复**：2.0.25 增加数量守卫，2.0.26 内置 349 条兜底，2.0.27 恢复铜陵学院到 350 条；但守卫仍是“相对当前长度”，未解决基线依赖加载顺序的问题。

**预防规则**

- 一个发布脚本生成全部版本文本；不一致直接失败。
- “只增不减”同时约束数量与内容（名称集合不得丢失）。
- 更新元数据中的 `apk/page` 必须与 `version` 同源生成，禁止手填。

**应补测试**：元数据一致性脚本（版本、build、APK URL、文档表）；构造旧 `version.json` 指向旧 APK，断言校验失败。

## L5 表单：固定宽度 + 全局缩放 + 未设菜单颜色

**现象**：手动添加课程表单文字挤压/溢出；下拉菜单出现白底白字；不同机型表现不同。

**根因**

- `SizedBox(width: 420)` 是桌面尺寸，手机可用宽度只有约 280dp；再叠加全局 `textScaler = 1.15`，三列下拉必然挤压。
- `DropdownButtonFormField` 的菜单背景与文字颜色未显式指定，暗色主题下菜单用了浅色表面色，文字也继承浅色。
- 只用一台设备、一个缩放比例验收，没有 320dp/2.0 的用例。

**已做修复**：`isExpanded: true`、`dropdownColor: surfaceContainerHigh`、`style` 与 `DropdownMenuItem` 显式 `onSurface`；内容可滚动；标签字号下调。

**预防规则**

- 对话框不写死像素宽；用 `ConstrainedBox(maxWidth: 420)` + 自适应，窄屏自动单列/两行。
- 菜单、弹窗、输入框统一用主题 token（`surfaceContainerHigh`/`onSurface`），不依赖默认继承。
- 验收必须包含 320dp 与 2.0 文字缩放；表单加 `RenderFlex overflow` 断言（Flutter 测试会把 overflow 当异常）。

**应补测试**：320×640、textScale 2.0 下打开表单无异常；切换深色后下拉项对比度可读；周次 `1-16`、`1-8,10-16`、非法输入各有断言。

## L6 专有字体：把“能显示”当成了“能分发”

**现象**：APK 长期打包 `FangSongCN.ttf`（中易 FangSong，name 表标注 Microsoft supplied / “Any other use is prohibited”）与 `TimesNewRoman.ttf`（Monotype）；Flutter 与 Android 各存一份，仅仿宋两份就多出约 21MB，另有两份 Times New Roman；GPL-3.0 项目却分发受限字体。

**根因**

- 选字体时只看效果，没有许可审查；族名 `FangSongCN`/`TimesNewRoman` 掩盖了真实来源。
- 没有“资源入包”清单，字体既进 Flutter assets 又进 Android assets，重复且难审计。
- 发布清单没有“字体许可”检查项。

**已做修复**：正文换 FandolFang（GPL-3.0 + 字体例外，SHA-256 与 CTAN 原件一致），西文换 Liberation Serif（SIL OFL 1.1，度量兼容）；族名保持不变，主题与小组件只改路径；`THIRD_PARTY_NOTICES.md` 记录来源/许可/SHA；旧字体从工作树移除。

**预防规则**

- 任何二进制素材入包前记录：来源、版本、许可、SHA-256、是否修改。
- 许可不兼容的素材不得进入构建；发布前解包 APK 核对字体清单。
- 同一字体只保留一份分发路径（Flutter asset 或 Android asset），避免双份。
- 清理中间产物（`_fangsong_cjk.ttf`、`_times_latin.ttf`），否则“已删除”只是表面。

**应补测试/检查**：`git ls-files` 无旧字体；APK 解包无旧字体且手工字体仅 4 个（另有 flutoryx 自带的 Mulish）；许可文本存在；生僻字回退截图。

## L7 盲改脚本：`replace()` 静默失败与编码损坏

**现象**：仓库积累了大量 `tool/patch_*.py`、`version_*.py`；部分中文正则变成乱码；有的补丁没匹配到也返回成功。

**根因**

- 用 `s.replace(a, b)` 批量改源码，不检查替换次数；匹配失败时脚本仍“成功”。
- 多次 UTF-8/GBK 往返导致中文变乱码。例：`lib/ui/import_web_screen.dart:205` 的翻周兜底正则在源码中被转成了 GBK 乱码（本应是“下一周/下周/后一周”），永远匹配不到真实按钮文字；当前该文件内已搜不到“下一周”。
- 版本脚本一版一改，重复逻辑没有单一入口。

**预防规则**

- 禁止无断言的字符串替换补丁；必须校验 `count == 1`，否则退出非零。
- 中文源码只走 UTF-8；提交前用工具检查典型乱码特征（例如把常用中文词显示为不相关汉字）。
- 版本/元数据用单一脚本生成，不复制粘贴。
- 改动优先用可审查的编辑，而不是“跑个脚本看看”。

**应补测试**：翻周兜底正则单测（用真实“下一周”文本）；CI grep 乱码特征；元数据一致性脚本。

## L8 文档滞后：政策版本与代码脱节

**现象**：应用已是 2.0.37，`PRIVACY.md` 仍写“适用版本 2.0.28（build 30）”；`THIRD_PARTY_NOTICES.md` 仍称“未复制 Kotlin/Compose 代码”，而 `lib/classy_parser.dart` 已是 `JwNewZfParser.kt` 的移植；应用内没有隐私政策入口。

**根因**

- 文档被当成“写完即完成”，没有和发布绑定。
- 版本号有四处来源，更新时只改代码。
- 合规检查不在发布清单里。

**已做修复**：`SDK.md`、`THIRD_PARTY_NOTICES.md` 已更新字体与 Classy 移植说明；`PRIVACY.md` 版本表与应用内入口仍待补。

**预防规则**

- 版本号单一来源；发布脚本同步文档表。
- 每次涉及数据流/依赖/素材的改动，同一 PR 更新 `PRIVACY.md`/`SDK.md`/`THIRD_PARTY_NOTICES.md`。
- 应用内提供隐私政策与 SDK 清单入口；无入口视为未完成。
- Classy 移植必须在声明中写明 GPL-3.0 改编。

**应补检查**：发布前 diff 文档版本表；应用内点两次可打开政策；声明与 `lib/` 实际文件一一对应。

## 五条硬规则

1. **先写验收，再改实现**：坐标、计数、缓存、版本都必须有可重复断言。
2. **一个状态只有一个写入者**：`schedule` 只能由 `AppController` 的派生函数改写。
3. **缓存键随内容变**：URL/查询参数/文件名不能是常量；名单下限是绝对常量。
4. **资源入包先过许可**：来源、许可、SHA、修改状态四件套。
5. **禁止盲改**：任何批量替换必须断言命中次数；中文只走 UTF-8。

## 复发风险最高的三处（当前）

| 位置 | 风险 | 触发条件 |
| --- | --- | --- |
| `AppController._withManual` 提前返回 | 调课静默丢失 | 用户从未添加手动课 |
| `_Timetable.build` 内新建 `GlobalKey` | 拖动中断/状态丢失 | 拖动中任何父级重建 |
| `SchoolRegistry` 相对数量守卫 | 名单回退 | 本地资源加载失败 + 远端旧 JSON |

这三处都不需要新功能，只需小改 + 测试；建议作为下一轮的第一批提交。
